# Primary sources and provenance policy

DPCompat treats version facts as executable compatibility data. Release records, feature boundaries, built-in rules, and third-party rules must remain traceable to a primary source.

## Mojang stable-release notes used by 0.3

- [Java Edition 1.21.4](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-4) — data-pack format 61.
- [Java Edition 1.21.5](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-5) — format 71; text-component event shape, tooltip display, entity equipment, saddle slot, recipes and GameTest changes.
- [Java Edition 1.21.6](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-6) — format 80 and strict JSON.
- [Java Edition 1.21.7](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-7) — format 81.
- [Java Edition 1.21.8](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-8) — format 81 hotfix.
- [Java Edition 1.21.9](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-9) — format 88.0, minor pack versions, metadata, spawn rotation and chain identifiers.
- [Java Edition 1.21.10](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-10) — format 88.0 hotfix.
- [Java Edition 1.21.11](https://www.minecraft.net/en-us/article/minecraft-java-edition-1-21-11) — format 94.1; gamerule registry names, tick-based world-border time, filtered loot and Environment Attributes.
- [Java Edition 26.1](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-1) — format 101.1, Java 25, world clocks and recipe changes.
- [Java Edition 26.2](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-2) — format 107.1 and sulfur-cube archetypes.

The same release URLs live in `dpcompat/data/releases.json`; feature records live in `dpcompat/data/features.json`; every built-in rule is mapped in `dpcompat/migrations/sources.py`. The registry refuses any rule without at least one source URL.

## Evidence hierarchy

1. stable-release technical notes;
2. reports generated by that stable release's official server JAR;
3. vanilla data bundled/generated by the stable release;
4. official snapshot notes only to investigate an undocumented transition;
5. reproducible in-game/GameTest evidence;
6. third-party documentation only as a discovery aid, never the sole proof for lossless behavior.

A PR must record the exact pack-format boundary, old/new examples, downgrade invariants, conflicts and non-default values, unit tests, and—where practical—matching server or GameTest evidence. A similar name is not version evidence.
